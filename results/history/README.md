# Superseded runs, kept as evidence

Every claim in the technical notes about something that went **wrong** points at a file
here. A defect described without the data that showed it is an assertion, and this
project does not make assertions.

| file | what it is | what it proves |
|---|---|---|
| `e2-degradation-run1-broken-targeting.csv` | first completed E2 run | Chosen faults report `ratio_to_baseline = 0.99999`, i.e. no damage at all. The targeting policy was selecting the largest-magnitude weights, which are exactly those with \|w\| ≥ 2 — the condition for bit 14 to be **already set**, so the flip divided by 2¹²⁸ instead of multiplying. See `docs/e2-degradation.md`. |
| `e2-degradation-run2-session-a.csv` | E2 with the corrected policy | Paired with `../e2-degradation.csv` (session B) it is the evidence for the inter-session noise figure: the identical configuration on different hardware moved baseline perplexity by 3.030 × 10⁻⁵ relative, while top-1 agreement was identical in all 30 configurations. |
| `e5-oracle-validation-spec-v1.csv` | oracle validation under spec v1 | Two of four corners failed. The aligned model's refusals were classified `degenerate` 63% of the time. |
| `e5-verdicts-spec-v1.csv` | per-probe verdicts, spec v1 | The diagnosis: all 63 misclassified refusals are 40–48 characters long, against a median of 139 for those classified correctly. The degeneracy floor of 40 letters sat inside the refusal length distribution — a refusal is short by construction. This is what the changelog in `src/bitflip/spec/oracle_spec.yaml` refers to. |
| `e5-oracle-validation-spec-v2.csv` | oracle validation under spec v2 | Five corners of six. The one that failed is `abliterated/harmful`: 46.0% compliance, 45.0% indeterminate. |
| `e5-verdicts-spec-v2.csv` | per-probe verdicts, spec v2, **batch 8 in arrival order** | The diagnosis, and the numbers spec v3 was built against. `base/benign` — an aligned model on harmless questions, no flips and no ablation — reports the same 52% compliance and 48% indeterminate as the corner that failed, with the two classes at medians of 1,079 and 800 characters. Same keywords, same bar, same order of length: the procedure marker alone separated them, so structure was standing in for substance. The same table holds the constraint v3 had to respect — a quarter of `base/harmful` refusals run past 481 characters. It is also the paired baseline for `experiments/e5_compare_specs.py`: only 341 of its 600 answers survive into the v3 run byte-identical, because the batch configuration changed, so the SHA column is what separates the specification's effect from regeneration. || `e5b-chosen-arm.kaggle-log.json` | the log Kaggle kept of the chosen arm of E5b, as served by `kaggle kernels output` | The run completed all six conditions and died in its summary on a field name that was guessed instead of read. It ran before the notebook checkpointed anything, so until the arm was re-run on 2026-09-04 this log was the only source of its counts. The per-probe table of that first run did not survive. |
| `e5b-chosen-counts-recovered-from-log.csv` | the chosen arm's count table, rebuilt from the log above by `experiments/e5b_recover_counts.py` | What the arm's result rested on between 2026-08-29 and 2026-09-04. The re-run's checkpoint, now `results/e5b-chosen-counts.csv`, matches it in every count and agrees with its perplexities to the six decimals the log printed — which is the second validation of the recovery, after the random arm's log reproducing its own checkpoint. |
| `e5b-random-arm.kaggle-log.json` | the same for the random arm | The run completed all fourteen conditions and died in its summary on the seed that had collapsed at dose 10, where the `decided` rule had no probe to take a share over. Its checkpoint survived; the log is kept because the same recovery script, applied to it, reproduces the checkpointed counts row for row and the perplexities to the six decimals printed — which is what validates the chosen arm's reconstruction. |

No generated text is stored in any of these files: the verdict tables carry the class,
the answer length and a truncated SHA-256, which is enough to re-verify a classification
and not enough to redistribute anything.
